=== Problem Formulation ===

# Problem Solving Agent

Type of goal-based agent that [finds sequences of actions]{.underline} that lead to desirable states.
- **Search**: Process of looking for sequence of actions.

**Goal Formulation**: Based on current situation and agent's performance measure

**Problem Formulation**: Deciding what actions and states to consider, given a goal

> **Example**: Romania Touring
> 
> Situation:
> On holiday in Romania. Currently in Arad, but have a non-refundable ticket to fly *out* of Bucharest tomorrow.
> 
> Goal Formulation: Be in Bucharest before the flight.
> 
> Problem Formulation:
> - States: Various cities
> - Actions: Drive between cities
> 
> Search: Sequence of cities

# Well-Defined Problems

A problem can be defined formally by five components:
1. Initial state
2. Actions
3. Transition model: description of what each action does (successor)
4. Goal test
5. Path cost

# Problem Abstraction

Remove as much detail as possible while retaining validity and usefulness.
- Validity: Can be expanded into a solution in a more detailed world.
- Useful: Carrying out actions in the solution is easier than the original problem.

=== Searching for Solution ===

# Search Tree

Generated by initial state and possible actions.
- Basic idea is we want to explore state space by expanding states.
- *How* we choose which state to expand is the **search strategy**

# Terms

**Frontier**: Set of all leaf nodes available for expansion at any given point.

**Repeated State**

**Loopy Path**: A $\to$ B $\to$ A

**Redundant Path**: More than one way to get from one state to another

> **Remember** — Redundant paths can be unavoidable (e.g., sliding-block puzzle)

# General Search Algorithms

## General Tree Search Algorithm

```clrs
function TREE—SEARCH(problem) returns solution \lor failure
	initialize frontier using initial state of problem
	// ...
	loop do
		// Guard: Nothing left to expand but no solution
		if frontier = \emptyset then return failure

		// "choose" is the domain of the search strategy
		choose leaf node and remove it from the frontier

		// Return: Goal found!
		if node contains goal state then return solution

		// Loop (else): Expand and continue
		expand chosen node, add resulting nodes to frontier
```

Notes:
- Algorithms that forget history are doomed to repeat it!
- This algorithm can turn a linear problem into an exponential one by hitting repeated states.

## General Graph Search Algorithm

An augmented version of General Tree Search Algorithm that remembers an explored set

```clrs
function GRAPH—SEARCH(problem) returns solution \lor failure
	initialize frontier using initial state of problem
	initialize explored set to be empty
	// ...
	loop do
		// Guard: Nothing left to expand but no solution
		if frontier = \emptyset then return failure

		// "choose" is the domain of the search strategy
		choose leaf node and remove it from the frontier

		// Return: Goal found!
		if node contains goal state then return solution

		// Remember node as explored
		add the node to the explored set

		// Loop (else): Expand and continue on non-repeats
		expand chosen node, add resulting nodes to frontier only if not in the frontier or explored set
```

## Child-Node Function

This function takes a parent node, and action, and returns the resulting child node.

```clrs
function CHILD—NODE(problem,parent,action) returns node
	return node with:
		STATE = problem.RESULT(parent.STATE, action),
		PARENT = parent,
		ACTION = action ,
		PATH—COST = parent.PATH—COST + problem.STEP—COST(parent.STATE,action)
```

## Frontier and Explored Set Implementation

Goal of Frontier: Next node to expand can be easily located in the frontier.
- Good Data Structure: Priority Queue, with search strategy picking priority

Goal of Explored Set: Efficient checked for repeated states
- Good Data Structure: Hash Table or Map

# Search Strategies

Picks the order of node expansion.

## Criteria

Strategies are evaluated along the following dimensions:
- completeness: does it always find a solution if it exists?
- optimality: does it always find a least-cost solution?
- time complexity: # of nodes generated
- space complexity: maximum # of nodes in memory

## Time and Space Complexity

Time and Space Complexity measured in terms of:
- b: maximum branching factor of the seach tree
- d: depth of the least-cost solution
- m: maximum depth of the state space (can be infinity)

Search cost refers to time, total cost refers to time + space.

# Depth-First Search

Expand deepest unexpanded node.

Frontier is a LIFO queue (stack) (new successors go on front)

Properties: Properties depend on whether we're doing graph-search or tree-search

Analysis (tree search):
- Complete: No, fails in infinite-depth spaces, or spaces with loops.
- Time: O(b^m). If we get unlucky, $m$ may be much larger than $d$.
	* If solutions are dense, may be able to beat BFS.
- Space: O(bm). Linear space
- Optimal: No. Not complete, so not optimal.

Analysis (graph search):
- Complete: No in indefinite-depth; yes in finite state spaces
- Time: O(b^m)
- Space: No longer linear due to explored set.
- Optimal: No. Not complete, so not optimal.

# Backtracking Search

Variant of DFS that generates only one succcessor at a time.
- Each partially-expanded node remembers which successor to generate next.

Space is $O(m)$, rather than $O(bm)$

Heuristic function $h(n)$: Estimated cost of cheapest path from node $n$ to goal.

# Best-First Search Algorithm

1. Initialize $Q$ with starting state (node).
2. While $Q != \emptyset$ do:
	1. Assign first element of $Q$ to $N$
	2. Guard: if $N ==$ goal, return SUCCESS
	3. Remove $N$ from $Q$
	4. Add children of $N$ to $Q$
	5. Sort entire $Q$ by $f(n)$
3. return FAILURE

# A*

Idea: Avoid expanding paths are are already expensive.

Evaluation Function: $f(n) = g(n) + h(n)$
- $f(n)$: Estimated total cost of path through $n$ to goal.
	* $g(n)$: Cost so far to reach $n$
	* $h(n)$: Estimated cost from $n$ to goal

> **Aside**: Improvement over GBF
> 
> This evaluation function works a lot better than Greedy Best-First because we *also* account for $g(n)$, the distance to $n$.
>

Analysis:
- Complete: Yes (unless there are infinite node with $f \le f(g)$
- Time: Exponential in length of the solution
- Space: Keeps all node in memory (will run out of space before it runs out of time)
- Optimal: Yes, under finite $B$ and positive path cost.

> Optimally efficient — No other optimal algorithm is guaranteed to expand fewer nodes than A*

## Admissible Heuristic

An admissible heuristic never overestimates the cost to reach the goal (i.e., it's optimistic).

Formally:

$$
\boxed{
	\text{Admissible: } h(n) \le h^*(n) \quad \forall \quad n
} \\
\small\textit{where $h*(n)$ is true cost to reach goal state from $n$}
$$

> **Example** - $h_{SLD}(n)$ is admissible because it never overestimates the actual road distance.

## Theorem: Optimality of A* (Tree-Search)

**Theorem**: If $h(n)$ is admissible, A* using tree-search is optimal.

> **Aside**: This is *not* true for A* using graph-search!
> 
> Remember that graph-search adds the condition that you can't repeat the same node.
> 
> This means it's possible to find a suboptimal route through a node first; locking yourself out of a more optimal path.
> 
> This is why we have consistency heuristics.

## Theorem: Optimality of A* (Graph-Search)

**Theorem**: If $h(n)$ is consistent, A* using graph-search is optimal.

> **Why?** — If $h(n)$ is consistent, it means whenever A* selects a node for expansion, the optimal path to that node has been found (you can't lock yourself into suboptimal choice).

=== Heuristic Functions ===

> **Question** — How do you design heuristic functions?

# Quality of Heuristic

Assume # of nodes generated by A* for a problem is N and the solution depth is d.

Then, b* is the effective branching factor that a uniform tree of depth d would have to have.

Thus:
$$
N + 1 = 1 + b^* + (b^*)^2 + ... + (b^*)^d
$$

(b* may vary across problems, but it fairly constant for sufficiently hard ones)

A well designed heuristic should have a value of b* close to 1.

# Domination 

$h_2$ **dominates** $h_1$ if $h_2(n) \ge h_1 (n)$ for all $n$
- This means $h_2$ is a better search and *never* expands more nodes than A* using $h_1$

> **Aside** — Both $h_1$ and $h_2$ have to be admissible

> **Aside**: If a collection of admissible heuristics don't have a "best" one, we can use all of them
> 
> Just pick the max!
> $$
>	h(n) = max{h_1(n),...,h_m(n)}

# Designing Admissible Heuristics

**Relaxed Problem**: A problem with fewer restrictions on the actions

Strategy: If you relax a problem, you can find a strategy for *that* problem and make it the admissible heuristic.

> **Example**: Designing Heuristics
> 
> In the 8-puzzle sliding-block problem, there are two heuristic function you could come up with:
> - $h_1 (n)$ = number of misplaced tiles
> 	* If we assume that each misplaced tile can be fixed with only a single move, that is the cheapest cost.
> - $h_2 (n)$ = sum of the distances of the tiles from their goal positions
> 	* This is called the Manhattan distance
> 
> We got h_1 by relaxing the rules and allowing a tile to move *anywhere*,
> 
> We got h_2 by relaxing the rules and allowing a tile to move to *any* adjacent square.
> 
> Of course, in the *actual* problem, we have to shuffle tiles around and do way more moves to avoid collisions.
> 
> > **Example**: Applying $h_1$ and $h_2$
> > 
> > Start State:
> > ```
> > 7 2 4
> > 5   6
> > 8 3 1
> > ```
> > 
> > Goal State:
> > ```
> >   1 2
> > 3 4 5
> > 6 7 8
> > ```
> > 
> > h_2(n) = 18
> > 
> > Individually, for example, the Manhattan distance of:
> > - "1" tile: 3 (left, up, up)
> > - "2" tile: 1 (right)
> > - etc.
