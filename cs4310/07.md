# Deadlock & Starvation

Deadlock: Two or more processes wait indefinitely for an event that can only be caused by only one of the waiting processes.

Starvation: Indefinite blocking
- A process may never be removed from the semaphore queue in which it is suspended.

Priority Inversion: Scheduling problem when lower-priority process holds a lock needed by a higher-priority process.
- Solved by priority-inheritance protocol

> Indivisibility: When we say a critical section must be indivisibly/atomically, we are talking about the code which holds and releases the lock.
> - The critical section itself can be big and doesn't need to be done in a single cycle, it can be preempted safely (though, this can lead to starvation).

> Priority Inversion Protocol: We temporarily assign the highest priority to the process currently executing in its critical section to prevent it getting starved.

## Readers and Writers

In this problem, a dataset if shared among a number of concurrent processes.
- Readers: Only read the dataset (they don't update it).
- Writers: Can read and write.

**Problem**: How do you let multiple readers read at the same time?
- Only one writer can access the shared data at the same time.

---

Variations:
- First: No reader kept waiting unless writer has permission to use shared object.
	- In other words, no reader needs to wait for other readers to finish simply because a writer is waiting.
	- Favor readers (starves writer)
- Second: Once writer is ready, it does the write ASAP.
	* In other words, if a writer is waiting to access the object, no *new* readers may begin reading.
	* Favor writers (starves readers)

> **Note** — Both may have starvation, leading to even more variations.
> - On some systems, the kernel provides reader/writer locks to resolve this.

---

### Solution to First Variation

Shared Data:
- Semaphore: `rw_mutex`
	* Checked by the writer, first reader, and last reader.
- Semaphore: `mutex`
	* Checked by all readers. For mutual exclusion when updating `read_count`.
- Integer: `read_count`
	* Lets a reader know if it's the first or last reader.

The idea basically, is the first reader will check if it's safe to get into the CS (`wait(rw_mutex)`). After this, all the readers won't have to wait for the `rw_mutex`, they'll only ever wait to update the `read_count`. The last reader will release the lock and allow the writer to do its thing again.
